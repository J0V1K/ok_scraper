# Plan: Date-range scraping + comprehensive metadata + inline OCR

## Context

Three motivations stack:

1. **Date-range over case-number batching.** The current `--year + --start + --count` model wastes effort on non-existent case numbers and produces output keyed by sequence rather than filing date. Detection_pilot indexes everything by filing month, so the corpus needs to land in `data/YYYY-MM-DD/<CASE>/` matching the SF layout. This unlocks direct reuse of `detection_pilot/scripts/*` against OK output.

2. **Broader case-type scope.** The research goal is comparative — civil vs. criminal vs. pro-se vs. represented — not a single homogeneous corpus. Default scope expands from CJ-only to **CJ + CV + CF + CM** (civil + criminal). Pro-se status is computed from the case page's attorneys section (free metadata).

3. **OCR is non-optional for OSCN.** A pilot over all 271 existing PDFs found that **every** OSCN-served PDF is an image-only scan (300 dpi grayscale, 2–3 pages typical, generated by PDFsharp wrapping a TIFF). `pdftotext` returns only form-feed bytes. We need OCR. Tesseract 5.5 is already installed locally and the OCR pilot showed:
   - 8/8 docs OCR'd cleanly
   - ~1.1 s/page, 3.2 s/doc median
   - 4 KB extracted text per doc (~50× reduction vs. PDF)
   - 70–78% letter fraction (good legal-text quality)

   The user has data-storage limitations, so the default behavior is **save text, discard PDF** unless OCR fails or quality is below threshold.

## What this plan changes

### 1. CLI shape

Replace sequential batching with date-range:

```bash
detection_pilot/.venv/bin/python ok_scraper/scraper.py \
  --start-date 2024-01-02 --end-date 2024-01-31 \
  --type CJ,CV,CF,CM \
  --county tulsa \
  --workers 3
```

Old `--year / --start / --count` arguments are removed. Sequential batching is no longer maintained.

Auto-resume: scan `data/YYYY-MM-DD/` directories with a `day_summary.json` and pick up at the first weekday in the requested range that isn't fully scraped.

### 2. Data layout

```
ok_scraper/data/
├── 2024-01-02/
│   ├── day_summary.json
│   ├── failed_cases.json    (only if any cases failed)
│   ├── CJ-2024-1234/

│   │   ├── 01-02-2024_1057134173.txt   (OCR'd text)
```

### 3. Per-day search loop

For each weekday in range, for each case-type in `--type`, hit `Results.aspx` once, parse `tr.resultTableRow`, filter out `result_shortstyle` containing "No Record.", filter by case-type prefix.

Sanity tripwire: if a single-day search returns ≥ 480 rows (just under OSCN's 500-row cap), log a warning and dump the raw HTML response to `data/YYYY-MM-DD/_search_dumps/<type>.html` for manual inspection. From `search_diagnostic.html` analysis, real CJ-only counts per day are well below 500 even before client filtering, but the watermark catches the day this assumption fails.

### 4. Comprehensive case metadata

Extend the case-page parser to capture, in addition to current fields:

- **Parties.** Each entry: `{name, type (Plaintiff/Defendant/Petitioner/etc.), pro_se}`. Pro-se inferred Python-side by computing parties − represented_parties.
- **Attorneys.** Each entry: `{name, bar_number, address, represented_parties[]}`. Bar number parsed from `(Bar #NNNNN)` in the attorney cell.
- **Counts** (criminal-specific). Each charge with statute reference, count number, disposition.
- **Issues** (civil-specific). Each issue with type code (INDEBTEDNESS, REPLEVIN, etc.), filed-by party, filed date.
- **Disposition / closure status.** For closed cases, the disposition reason if surfaced.
- **Bond info** (criminal-specific). Bond amount and status if present.
- **Hearings.** Any future or past scheduled hearings exposed in the page.
- **Rollups.** `any_pro_se`, `all_represented`, `count_pro_se_parties`, `n_attorneys` for cheap downstream stratification.

All written into `register_of_actions.json` under `metadata`.

### 5. Inline OCR pipeline

After `download_pdf` succeeds, immediately:

1. Extract page TIFFs: `pdfimages -tiff <pdf> <tmpdir>/p`
2. For each page TIFF: `tesseract <tiff> stdout -l eng --psm 6`
3. Concatenate with form-feed (`\f`) between pages.
4. Quality check:
   - `chars >= 200` and `letter_frac >= 0.4` and `repl_frac <= 0.05` → status `ok`
   - `chars == 0` → status `empty`
   - other thresholds violated → status `low_quality`
   - Tesseract / pdfimages crashed → status `error`
5. If status is `ok`: write `.txt`, delete `.pdf`.
6. If status is anything else: keep both `.pdf` and (whatever) `.txt`, mark in metadata for later OCR re-pass with stronger settings (e.g., `--psm 1` automatic page segmentation, or cloud OCR).

Per-action telemetry added to register_of_actions.json:
```json
{
  "doc_id": "1057134173",
  "doc_filename": "01-02-2024_1057134173.pdf",
  "text_filename": "01-02-2024_1057134173.txt",
  "text_chars": 4523,
  "text_pages": 3,
  "text_letter_frac": 0.77,
  "text_extraction_status": "ok",
  "text_extraction_elapsed_s": 3.2,
  "ocr_engine": "tesseract-5.5"
}
```

OCR is CPU-bound and runs in a `ThreadPoolExecutor` (or just sequentially under the existing `DOWNLOAD_SEMAPHORE`). At 3 s/doc and 50 docs/day/type × 4 types = 200 docs/day, OCR adds ~10 min wall-clock per scraped day per worker. Acceptable.

### 6. High-value filter expansion

Add criminal-specific patterns to `HIGH_VALUE_BRIEF_RE`:
- `MOTION TO SUPPRESS`
- `MOTION TO QUASH`
- `MOTION IN LIMINE` (already)
- `SENTENCING MEMORANDUM`
- `INFORMATION` (charging document, prose-rich)
- `PLEA AGREEMENT`

Pleadings for criminal: `INFORMATION` is the criminal analog of a civil complaint. Add to `HIGH_VALUE_PLEADING_RE`.

After the first day of multi-type scraping, dump the `proceedings` text of all rows where `is_high_value=False` to `data/_filter_audit/`. Spot-check whether any patterns are slipping through and tighten/loosen as needed.

### 8. Migration script for existing data

`ok_scraper/migrate_existing.py` — one-shot:

1. Walk `data/CJ_*/` dirs.
2. Read each `register_of_actions.json`, parse `metadata.filing_date` (or fall back to first action date).
3. `mv` the directory → `data/YYYY-MM-DD/<CASE-NUMBER>/` (un-substituting underscore back to dash in the case number).
4. OCR every PDF in the migrated directory using the same pipeline as the new scraper.
5. Update `register_of_actions.json` schema in place: add `text_*` fields per action, set `doc_filename: null` and delete the PDF when OCR succeeded.
6. Leave `parties`, `attorneys`, `counts`, etc. blank for migrated cases (we don't have the case-info HTML anymore). Cases will need re-scraping later if those fields are required for analysis. A `metadata.migrated_from_v1: true` flag flags them.

Estimated time: 271 PDFs × 3 s OCR + dir moves = ~15 min. One-shot, runs once.

### 9. Worker dispatch by date range

Replace the current case-number-range chunking with a date-range chunking:

```python
weekdays = list(weekday_dates(args.start_date, args.end_date))
chunks = split_into_n_contiguous(weekdays, args.workers)
for i, chunk in enumerate(chunks):
    cmd = [..., "--start-date", chunk[0], "--end-date", chunk[-1]]
    spawn(cmd)
```

Each child runs `--workers 1` against its assigned date span. Per-worker logs in `data/_worker_logs/worker_<i>_<startdate>_<enddate>.log`.

## Implementation order

1. **Migration + OCR pilot on existing data first.**
   - Build the OCR helper (`ocr_pdf(pdf_path) -> (text, metrics)`) as a standalone function.
   - Build `migrate_existing.py`, run it.
   - This produces the first batch of text data and validates OCR throughput at scale (271 docs).
   - **Output**: 271 OCR'd documents in v2 layout, ready to feed into the detection pipeline.
2. **Search-driven scraper for new data.**
   - Implement `--start-date / --end-date`, the per-day search loop, Results.aspx parser, type-prefix filtering, watermark warning.
   - New data layout `data/YYYY-MM-DD/<CASE>/` with day_summary.json + failed_cases.json.
   - Worker dispatcher chunks by weekdays.
3. **Comprehensive case metadata.**
   - Extend page-evaluate JS for parties / attorneys / counts / issues / disposition.
   - Python-side pro-se inference + rollups.
4. **Inline OCR in the scrape path.**
   - Wire the OCR helper into `download_pdf` post-success.
   - Default: delete PDF on OCR success.
   - Schema v2 emission.
5. **Filter expansion + first-day audit.**
   - Add criminal terms to high-value regex.
   - First multi-type day dumps non-matching descriptions for review.

## Verification

1. **Migration verification.** After step 1, confirm:
   - All 271 PDFs migrated to date-keyed dirs.
   - Per-doc telemetry shows ≥ 95% `text_extraction_status=ok`.
   - Total disk size dropped substantially (~127 MB PDFs → ~1–5 MB text + still-failing PDFs).
   - Detection-pilot's `extract_pdf_texts_from_manifest.py` (or equivalent) successfully reads at least one OK case from the migrated data.

2. **Single-day pilot of new flow.** Run a one-day, four-type pilot:
   ```bash
   detection_pilot/.venv/bin/python ok_scraper/scraper.py \
     --start-date 2024-01-02 --end-date 2024-01-02 \
     --type CJ,CV,CF,CM --county tulsa --workers 1
   ```
   Confirm:
   - `day_summary.json` shows realistic counts per type.
   - No watermark warnings (real-CJ count well under 500/day).
   - OCR success rate matches the pilot (≥ 95%).
   - `metadata.parties` and `metadata.attorneys` populated for at least one case in each type.
   - Pro-se inference gives at least one `any_pro_se=true` case (most likely from PO; may not appear in CJ/CV/CF/CM but for sanity).

3. **Three-day backfill probe.** Same command, range Jan 2 → Jan 4, workers=3. Confirm:
   - No IP-block events.
   - All 3 days' day_summary.json populated.
   - Cross-type metadata accuracy spot-check on 5 random cases.

4. **Storage check.** After step 3, total OK data dir should be in the 100–500 MB range, not GB.

If verification passes, do a 2-week probe (10 weekdays) and check for stable behavior, then commit to longer backfills.

## Tunable knobs

- `PER_CASE_PDF_CAP` (existing, keep at 5)
- `MAX_CONSECUTIVE_GATES` (existing, keep at 2)
- `OCR_PSM` (default `--psm 6`, may need `--psm 1` for some layouts)
- `OCR_LANGS` (default `eng`)
- `--keep-pdfs` flag (default off; on for debugging)
- `--ocr-only` flag for re-running OCR on existing PDFs without re-scraping

## Open questions parked for now

- **Cloud OCR** if Tesseract quality is insufficient for any subset (criminal handwritten endorsements, faded older scans). Decision after we have a few hundred OCR'd docs and can spot-check quality.
- **Pagination of Results.aspx** if any single day's filtered count actually approaches 500. Tripwire above catches this; we revisit if it ever fires.
- **Migration backfill of parties/attorneys** for the 271 already-scraped cases. Decision: re-scrape them after the new flow is live, vs. leave them as v1-migrated with blank metadata. Probably re-scrape to keep the corpus uniform.
